Commerce primitives in Go

A commerce engine you can hold in your head.

One binary, one PostgreSQL database, one third-party dependency. Products and variants, inventory, carts, checkout, orders, payments, fulfilment and durable events — with integrations as ordinary Go packages you wire in main(). No Redis to stand up, no search cluster, no vendor SDK in your dependency graph.

What it does that the others mostly don’t

Three things unusual in an engine this size, and that none of Vendure, Saleor or Medusa ships in core.

A transactional outbox you can repair

A state change and the event describing it commit together. A dispatcher claims unsent rows with FOR UPDATE SKIP LOCKED, so two instances never double-deliver — and dead letters are inspected and un-parked through the API rather than through a SQL runbook.

An audit trail over 27 entity kinds

Who changed what, merged with the outbox into one order timeline by the transaction timestamp both rows take. Not an add-on: the engine records it because an operator will eventually have to answer for a number.

A doctor that checks its own invariants

Fifteen checks, among them a stock-ledger reconciliation, a refund-total reconciliation, and “every admin route names the rights it needs”. The store says when it has drifted instead of waiting to be asked.

A store is a Go program

No YAML, no plugin registry, no runtime discovery. What the store is made of is what the code says it is made of. 

app, err := gocommerce.New(
    gocommerce.Config{
        DBURL:       os.Getenv("DATABASE_URL"),
        Currency:    "USD",
        AdminTokens: []string{os.Getenv("GOCOMMERCE_ADMIN_TOKEN")},
    },
    stripe.New(stripe.Config{ /* ... */ }),
    sendgrid.New(sendgrid.Config{ /* ... */ }),
    translations.New(),
)
log.Fatal(app.ListenAndServe())

And what it doesn’t do

Published for the same reason as everything above. A comparison that lists only strengths is an advertisement; this is the part you would otherwise find out in week three.

  • No multi-currency. One settlement currency per store, snapshotted onto every order. Deliberate — mixed-currency checkout reopens every rounding decision on the money path — but if you sell in three currencies, this is the wrong engine today.
  • No gift cards, loyalty or store credit. A gift card is a tender, not a discount, so it lands on the payment path rather than beside the promotions. Not built, and not faked with a discount code.
  • No subscriptions. Orders are one-shot. Recurring billing is a domain of its own, not a flag on a product.
  • No marketplace. One seller per store. Several independent sellers with their own orders and payouts is a different engine, not a module.
  • API keys are configuration, not records. Every integration shares one token, rotating it needs a restart, and revoking one revokes all of them. Fine for a single deployment, wrong for a dozen integrations.
  • Module screens cover a list and a form. A module can contribute an admin screen without touching the panel — but a chart, a drag-to-reorder or a bespoke editor still needs core to build it.
